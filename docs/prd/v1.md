# ReadyPlayerTwo V1 Product Requirements Document

## Overview

ReadyPlayerTwo V1 is a locally run, macOS-only Companion prototype that must prove two product qualities:

1. Orion and Athena feel polished, fluid, and naturally present across the Desktop Stage.
2. A person can explicitly Summon the Companion and hold a natural OpenAI Realtime Voice Session.

V1 is a Summon-Only Experience and a Screen-Blind Experience. The Companion may move silently, but it never initiates social contact, observes screen content, listens for a wake phrase, or learns from the person. It is a locally development-signed app with a persistent Status Menu and no App Store dependency.

The acceptance target is macOS 15 or newer on Apple Silicon. V1 supports exactly one Companion across connected displays, uses the existing Orion and Athena sprite assets, and keeps conversational context only for the active Voice Session.

## Glossary

**Companion**  
A character that provides socially natural spoken company while a person works at their desktop. It is not an assistant, chatbot, or desktop pet.

**Work Session**  
A period in which a person uses their desktop to pursue work, regardless of profession or application.

**Summon-Only Experience**  
An interaction model in which the person initiates every conversation, while the Companion may remain visibly present and move without initiating contact.

**Screen-Blind Experience**  
A Companion experience that receives no visible content or semantic information from the desktop. Display geometry needed for the Desktop Stage is not screen observation.

**Roaming Presence**  
The default out-of-conversation state in which the Companion remains visible and moves silently without initiating contact.

**Park**  
A person-directed state in which the Companion remains visible at a fixed location without moving autonomously.

**Hide**  
A person-directed state in which the Companion leaves the Desktop Stage while the Status Menu remains available and a later Summon remains possible.

**Summon**  
A person-initiated request for the Companion's attention that may happen at any time.

**Summoned Conversation**  
A user-led exchange that begins after a Summon and follows the person's intent.

**Voice Session**  
A live spoken exchange whose microphone access begins only after the person intentionally starts an interaction.

**Desktop Stage**  
The desktop-wide area in which a Companion can appear and move independently of any single application window.

**Status Menu**  
The persistent macOS menu bar control surface for Summon, presence controls, character and voice preferences, diagnostics, and Quit.

## Problem Statement

People doing focused work across spreadsheets, design tools, code editors, documents, and other applications can benefit from the feeling of an office mate nearby. Existing assistants are commonly trapped inside one application, behave primarily as productivity tools, or require invasive context collection before they can appear responsive.

ReadyPlayerTwo must prove that a desktop Companion can feel fluid and socially present without observing the screen, listening continuously, or interrupting the person. The hardest parts are not broad assistant capability. They are polished desktop-wide character dynamics, trustworthy lifecycle behavior, transparent input handling, and natural low-latency voice.

The prototype must also establish a safe technical boundary. The standard OpenAI API key must not enter the app process, microphone use must always follow explicit intent, transparent character windows must not interfere with work, and every failure path must leave both the desktop and microphone in a safe state.

## Solution

Build V1 as a locally run, Dockless macOS app with a persistent Status Menu. Orion or Athena maintains a silent Roaming Presence across the Desktop Stage while the person works in any application. The person can Park, Hide, move, or switch the Companion at any time.

A Summon from the character, a configurable global shortcut, or the Status Menu starts a user-led Voice Session through OpenAI Realtime over WebRTC. The microphone begins only after Summon, the person speaks first, and a conversation bubble with a real audio-driven waveform communicates Connecting, Listening, Thinking, Speaking, Muted, Error, Retry, and End states.

The app uses native Swift, AppKit, and SpriteKit. A loopback-only credential broker mints short-lived Realtime client secrets while keeping the standard OpenAI API key outside the app. `CompanionRuntime` provides one high behavioral Seam for person actions, platform events, production Adapters, and deterministic tests.

V1 performs no Check-ins, screen capture, OCR, window inspection, availability inference, ambient listening, persistent conversation history, or Companion Memory. Its purpose is to validate character presence and summoned voice before broader autonomy or contextual awareness is considered.

## User Stories

### US-001: App-agnostic companionship

As a person working in any profession or application, I want an app-agnostic Companion, so that companionship is not tied to one workflow.

Acceptance criteria:

- [ ] The Companion can remain present while any ordinary foreground application is active.
- [ ] Core behavior requires no integration with, knowledge of, or control over the active application.

### US-002: Local app without App Store publication

As a developer evaluating V1, I want to run a local macOS app without App Store publication, so that I can validate the experience privately.

Acceptance criteria:

- [ ] V1 builds as a locally development-signed macOS app bundle.
- [ ] Running V1 requires no App Store account, submission, installer, or notarization workflow.

### US-003: One supervised launch command

As a developer, I want one terminal command to build, launch, and supervise the app and broker, so that local execution is reproducible.

Acceptance criteria:

- [ ] One command builds the app, starts the loopback credential broker, launches the app, and supervises both processes.
- [ ] Terminal interruption stops the Voice Session, microphone, app, windows, and broker without leaving an orphaned process.

### US-004: Singleton runtime

As a person, I want exactly one Companion and Status Menu after repeated launches, so that duplicate runtimes never appear.

Acceptance criteria:

- [ ] A second launch does not create another Status Menu item, Companion, audio engine, broker, or Realtime connection.
- [ ] The original runtime remains usable after a duplicate launch attempt.

### US-005: Dockless lifecycle

As a person, I want a Dockless app with no conventional main window, so that the Companion does not add another application workspace.

Acceptance criteria:

- [ ] The running app has no Dock icon.
- [ ] The app opens no conventional main window, while allowing a compact settings panel.
- [ ] The Companion appears within two seconds after executable launch on the target Mac.

### US-006: Persistent Status Menu

As a person, I want a persistent Status Menu with complete controls, so that I can manage the Companion from one predictable place.

Acceptance criteria:

- [ ] The Status Menu remains available while the Companion is Roaming, Parked, Hidden, or in a Voice Session.
- [ ] It exposes Summon or End Conversation, Roam, Park, Hide or Show, Orion or Athena, Move to Current Display, shortcut, voice, audio-device, diagnostics, and Quit controls.
- [ ] Connection and microphone status reflect real runtime state.

### US-007: Configurable global Summon shortcut

As a person, I want a configurable global Summon shortcut with conflict detection, so that I can reach the Companion from any application.

Acceptance criteria:

- [ ] The initial shortcut is Control + Shift + Space.
- [ ] The person can change the shortcut and receives a clear conflict state when it is unavailable.
- [ ] Shortcut registration requires neither Accessibility nor Input Monitoring permission.

### US-008: Equivalent Summon inputs

As a person, I want character click, shortcut, and Status Menu Summons to behave identically, so that interaction is predictable.

Acceptance criteria:

- [ ] Every Summon input enters the same `CompanionRuntime` behavior path.
- [ ] Summon works from Roaming, Parked, and Hidden states.
- [ ] Simultaneous or repeated inputs cannot create duplicate Voice Sessions.

### US-009: Silent Roaming Presence

As a person, I want silent Roaming Presence by default, so that the Companion feels present without initiating contact.

Acceptance criteria:

- [ ] A fresh launch shows Orion in Roaming Presence.
- [ ] Roaming uses deliberate movement bursts separated by quiet holds.
- [ ] A one-hour Roaming session produces no speech, Check-in, microphone request, or Voice Session.

### US-010: Park and drag-to-Park

As a person, I want to Park the Companion through a command or drag, so that it remains visible at a location I choose.

Acceptance criteria:

- [ ] Park stops autonomous travel while keeping the Companion visible.
- [ ] Dragging the Companion moves it to a reachable location and enters Park.
- [ ] A safe Park position persists across later launches.

### US-011: Hide without quitting

As a person, I want to Hide the Companion while retaining the Status Menu and Summon, so that I can clear the Desktop Stage without quitting.

Acceptance criteria:

- [ ] Hide removes the Companion from the Desktop Stage without ending the process.
- [ ] The Status Menu and global shortcut remain available while Hidden.
- [ ] Summon from Hidden reveals the Companion for the Voice Session.

### US-012: Presence restoration

As a person, I want ending a Voice Session to restore my previous presence state, so that conversation does not change my preference.

Acceptance criteria:

- [ ] End returns a previously Roaming Companion to Roaming.
- [ ] End leaves a previously Parked Companion parked at its prior safe position.
- [ ] End returns a previously Hidden Companion to Hidden.
- [ ] Hide during voice ends the Voice Session safely before hiding.

### US-013: One Companion across displays

As a person with multiple displays, I want one Companion across my display topology, so that it never duplicates.

Acceptance criteria:

- [ ] Exactly one Companion exists regardless of connected display count.
- [ ] Fresh launch and Summon select the display containing the pointer.
- [ ] Autonomous Roaming remains on one display at a time.

### US-014: Explicit display relocation

As a person, I want Summon and Move to Current Display to relocate the Companion safely, so that it remains near my current work.

Acceptance criteria:

- [ ] Move to Current Display relocates the Companion to the display containing the pointer.
- [ ] Summon from another display may relocate it before conversation begins.
- [ ] Relocation uses a short edge fade rather than unsupported cross-display locomotion.

### US-015: Display topology resilience

As a person, I want the Companion to remain reachable after display changes, so that it is never stranded offscreen.

Acceptance criteria:

- [ ] Display removal, rotation, resolution, scale, and arrangement changes recompute the Desktop Stage.
- [ ] Negative display coordinates are supported.
- [ ] The Companion remains within safe visible bounds and keeps a consistent point size across display scales.

### US-016: Transparent click-through input

As a person, I want transparent character pixels to pass desktop input through, so that the Companion does not interfere with work.

Acceptance criteria:

- [ ] Each frame uses an alpha-derived interactive hit region with at most 8 points of forgiving padding.
- [ ] Text selection, scrolling, dragging, resizing, and file drops behind transparent pixels reach the underlying application unchanged.
- [ ] Clicking visible character pixels Summons, while the character panel does not take keyboard focus.

### US-017: Spaces and full-screen behavior

As a person, I want the Companion to follow macOS Spaces conventions, so that its presence matches the workspace I am using.

Acceptance criteria:

- [ ] Roaming and Park follow the active regular Space without duplication.
- [ ] Ordinary presence hides in another application's native full-screen Space.
- [ ] An explicit Summon may reveal the Companion in that full-screen Space for the Voice Session.

### US-018: System lifecycle safety

As a person, I want lock, sleep, screen saver, and Mission Control transitions handled safely, so that the app never becomes intrusive or unsafe.

Acceptance criteria:

- [ ] Screen lock, screen saver, Mission Control, and sleep pause or hide the Desktop Stage as appropriate.
- [ ] Sleep or lock ends an active Voice Session and closes the microphone.
- [ ] Wake or unlock never reconnects or reopens the microphone automatically.

### US-019: Existing character art only

As a person, I want V1 to use the existing Orion and Athena sprites, so that the intended character designs are preserved.

Acceptance criteria:

- [ ] V1 uses the supplied transparent sprite frames and manifests.
- [ ] V1 adds no new character sprites, procedural art, mouth animation, or lip synchronization.

### US-020: Asset contract validation

As a developer, I want every sprite contract validated before display, so that malformed assets fail safely.

Acceptance criteria:

- [ ] The runtime validates all expected frames, dimensions, anchors, frame rates, and referenced states before showing a character.
- [ ] A missing or invalid required asset produces an actionable failure instead of a partial or corrupted animation.

### US-021: Stable refresh-synchronized motion

As a person, I want refresh-synchronized, device-pixel-aligned movement, so that sprites do not shimmer, jitter, or drift.

Acceptance criteria:

- [ ] Position updates follow the active display refresh rate while sprite frames use manifest-defined frame rates.
- [ ] Rendered positions align to device pixels.
- [ ] Grounded foot-anchor drift remains at or below 1 point.

### US-022: Polished transition bridging

As a person, I want missing pose transitions bridged discreetly, so that asset limitations are not visually distracting.

Acceptance criteria:

- [ ] Unavoidable discontinuities use 150 to 250 millisecond crossfades or intentional occlusion.
- [ ] No frame flash, crop jump, opaque rectangle, alpha halo, or one-frame pose reversal remains in accepted transitions.

### US-023: Conversational pose semantics

As a person, I want poses to communicate attention without lip synchronization, so that conversation still feels embodied.

Acceptance criteria:

- [ ] Summon settles the Companion into an attentive pose.
- [ ] Neutral poses represent attention and listening, while suitable happy poses may accompany speech.
- [ ] Autonomous travel stops throughout a Voice Session.

### US-024: Seamless character switching

As a person, I want character switching to preserve runtime state, so that choosing Orion or Athena is seamless.

Acceptance criteria:

- [ ] Switching preserves presence state, Voice Session state, and safe placement.
- [ ] The incoming character grounds itself through a short fade.
- [ ] The selected character persists across launches.

### US-025: Reduce Motion support

As a person using Reduce Motion, I want a calmer Desktop Stage, so that the Companion respects my accessibility preference.

Acceptance criteria:

- [ ] Reduce Motion replaces autonomous traversal with static visible presence.
- [ ] Required transitions use simple fades rather than energetic movement.
- [ ] Summon, Voice Session, Park, Hide, and Show remain fully usable.

### US-026: Character-specific legal motion

As a person, I want each character to use only movement supported by its assets, so that motion remains visually plausible.

Acceptance criteria:

- [ ] Orion is limited to walking, upward display-edge climbing, wall clinging, jumping downward, and landing.
- [ ] Orion never visibly climbs downward or invents a ledge exit.
- [ ] Athena is limited to walking, takeoff, vertical gliding, hover, landing, and slow airborne drift.
- [ ] Athena never uses fast horizontal flight.

### US-027: Immediate Voice Session response

As a person, I want Summon to begin connecting immediately, so that the Companion feels attentive.

Acceptance criteria:

- [ ] Summon begins connection without waiting for a locomotion sequence to finish.
- [ ] The Companion reaches an attentive pose within 350 milliseconds.
- [ ] A visible Connecting state appears while Realtime setup is in progress.

### US-028: Person-led conversation

As a person, I want to speak first and see clear Voice Session states, so that the Companion never begins an unsolicited conversation.

Acceptance criteria:

- [ ] The Companion emits no greeting or speech before the person speaks.
- [ ] The bubble represents Connecting, Listening, Thinking, Speaking, Muted, Error, Retry, and End accurately.

### US-029: Real audio-driven waveform

As a person, I want the waveform to follow real audio energy, so that it accurately communicates listening and speaking.

Acceptance criteria:

- [ ] Input waveform motion follows microphone energy while Listening.
- [ ] Output waveform motion follows playback energy while Speaking.
- [ ] The waveform stops when its corresponding audio stops.

### US-030: Natural turn-taking and barge-in

As a person, I want natural turn detection and barge-in, so that pauses are respected and I can interrupt.

Acceptance criteria:

- [ ] Semantic VAD initially uses low eagerness.
- [ ] Natural pauses do not routinely commit a turn prematurely.
- [ ] New person speech cancels current model playback and stale buffered audio.
- [ ] Audible Companion speech stops within 250 milliseconds at p95 during controlled barge-in tests.

### US-031: Voice controls and timeouts

As a person, I want explicit controls and inactivity timeouts, so that I remain in control of the microphone.

Acceptance criteria:

- [ ] Mute prevents microphone audio from being sent while preserving clear state.
- [ ] End closes the active Voice Session and restores prior presence.
- [ ] No first speech for 60 seconds ends the session.
- [ ] Two minutes without speech after conversation begins ends the session.

### US-032: Configurable Realtime model and voice

As a developer, I want the Realtime model and voice to remain configurable, so that provider choices can evolve independently of product logic.

Acceptance criteria:

- [ ] Neither model nor voice is hard-coded inside `CompanionRuntime`.
- [ ] Missing required configuration produces a Voice Not Configured state without disabling visual presence.
- [ ] Supported changes are available through local settings.

### US-033: Recoverable external failures

As a person, I want external failures to preserve visual presence and offer recovery, so that failures do not require restarting the app.

Acceptance criteria:

- [ ] Permission denial, broker failure, authentication failure, network loss, rate limiting, peer loss, and audio-device removal each produce a concise nonspoken error.
- [ ] Motion and presence controls remain usable after failure.
- [ ] The microphone closes on unrecoverable network or audio-route failure.

### US-034: Explicit Retry and session uniqueness

As a person, I want recovery to be explicit and sessions unique, so that the app never silently listens or opens duplicate connections.

Acceptance criteria:

- [ ] Retry requires an explicit person action.
- [ ] Failure, sleep, lock, or wake never silently reconnects.
- [ ] A second Summon during an active Voice Session reveals or focuses the current session without opening another connection.

### US-035: Natural live voice quality

As a person, I want a stable low-latency conversation, so that voice feels natural rather than mechanical.

Acceptance criteria:

- [ ] A normal live exchange lasts at least ten turns.
- [ ] Across 20 controlled turns on stable broadband, response audio begins within 1.5 seconds median and 2.5 seconds at p95 after end of speech.
- [ ] No start clipping, end clipping, echo loop, repeated segment, stale buffer, or overlap with an old response is audible.

### US-036: Microphone access only after Summon

As a privacy-conscious person, I want microphone permission requested only after explicit intent, so that launch and Roaming Presence require no audio access.

Acceptance criteria:

- [ ] Launch, Roam, Park, Hide, Show, and character switching never request microphone permission.
- [ ] The first Summon that needs voice triggers the macOS microphone consent flow.
- [ ] V1 contains no ambient-listening or spoken wake-phrase path.

### US-037: Prompt microphone teardown

As a privacy-conscious person, I want the microphone closed promptly after interaction ends, so that listening never outlives my intent.

Acceptance criteria:

- [ ] End, Hide, lock, sleep, Quit, unrecoverable failure, and audio-route failure stop capture.
- [ ] Microphone closure is observable within 500 milliseconds for every required teardown path.
- [ ] Quit leaves no audio engine or active capture process.

### US-038: Verifiable Screen-Blind Experience

As a privacy-conscious person, I want companionship without desktop observation, so that visual privacy is preserved.

Acceptance criteria:

- [ ] V1 requests no Screen Recording, Accessibility, Input Monitoring, Camera, or file-access permission.
- [ ] V1 captures no pixels and does not enumerate application windows, inspect app content, classify the screen, or monitor Inactivity.
- [ ] When asked about visible content, the Companion states plainly that it cannot see the screen.

### US-039: No sensitive conversational persistence

As a privacy-conscious person, I want sensitive conversational data minimized, so that local storage does not become a private-data archive.

Acceptance criteria:

- [ ] Audio, transcripts, conversation content, conversation history, Companion Memory, client secrets, and the standard API key are never written to disk.
- [ ] Logs contain no audio, transcript, conversation content, API credential, or client secret.
- [ ] Only privacy-redacted lifecycle, performance, and recoverable diagnostic events may be logged.

### US-040: Standard API key isolation

As a developer, I want the standard OpenAI API key confined to the credential broker, so that the app never receives a reusable provider secret.

Acceptance criteria:

- [ ] The standard key never enters the app bundle or app process.
- [ ] The launcher explicitly removes `OPENAI_API_KEY` from the app process environment.
- [ ] The loopback broker alone reads the standard key from the terminal environment.

### US-041: Short-lived direct Realtime connection

As a privacy-conscious person, I want direct media transport with short-lived credentials, so that the broker cannot observe conversation audio.

Acceptance criteria:

- [ ] The broker binds only to `127.0.0.1` and requires a random per-launch bearer.
- [ ] It allowlists model, voice, and session configuration and returns only a short-lived Realtime client secret.
- [ ] The app connects directly to OpenAI over WebRTC.
- [ ] The broker never proxies, records, or logs media.

### US-042: Accurate provider disclosure

As a person, I want accurate provider data-control information, so that I can understand the external privacy boundary.

Acceptance criteria:

- [ ] Developer diagnostics and future privacy copy do not imply that voice processing is local.
- [ ] Current provider training, application-state retention, abuse-monitoring retention, and Zero Data Retention eligibility are described accurately.
- [ ] Provider statements are reviewed against current official documentation before external distribution.

### US-043: Accessible and polished presentation

As a person using VoiceOver, keyboard navigation, different appearances, or scaled displays, I want a usable and visually polished experience, so that my setup is supported.

Acceptance criteria:

- [ ] Status Menu, bubble controls, settings, and actionable states have accurate VoiceOver labels and keyboard operation.
- [ ] Light mode, dark mode, busy backgrounds, Retina, mixed-scale displays, and Reduce Motion pass manual review.
- [ ] Bubble placement remains inside safe bounds and avoids the character's face, menu bar, and Dock.

### US-044: Resource efficiency and soak stability

As a person, I want low resource use and stable multi-hour operation, so that the Companion can remain present throughout a Work Session.

Acceptance criteria:

- [ ] Idle or Park CPU settles below 2 percent on the baseline Apple Silicon Mac.
- [ ] Ordinary Roaming CPU remains below 5 percent and resident memory remains below 200 MB.
- [ ] A two-hour soak shows no continuous memory growth, duplicate runtime, focus theft, blocked desktop input, lost Companion, orphaned process, unintended speech, unintended microphone access, or crash.

### US-045: Deterministic quality gates

As a developer, I want high-Seam tests and reliable quality gates, so that each atomic change can be shipped confidently.

Acceptance criteria:

- [ ] Product behavior is testable through `CompanionRuntime` and packaged-app Interfaces without inspecting private Implementation state.
- [ ] Offline suites are deterministic, and live OpenAI tests are separately opt-in.
- [ ] Formatting, linting, unit, integration, render, broker, packaged-app, and security checks pass without flakiness.
- [ ] Each implementation slice follows one-test, minimal-implementation TDD before refactoring.

## Implementation Decisions

- V1 targets macOS 15 or newer on Apple Silicon and uses a locally development-signed app bundle.
- Swift 6.3 with strict concurrency is the implementation language. A thin Xcode app shell owns packaging, lifecycle, microphone consent, and packaged-app tests, while internal Modules use Swift Package Manager.
- AppKit owns lifecycle, the Status Menu, transparent panels, display geometry, Spaces, system events, and pointer interaction.
- SpriteKit renders manifest-driven character animation in a transparent view. SwiftUI is limited to the compact settings interface.
- Agent-app activation removes Dock presence. A persistent macOS status item provides the Status Menu.
- One character-sized transparent, borderless, non-activating panel follows the Companion. V1 does not use a desktop-sized overlay.
- Per-frame alpha hit masks control panel mouse handling. The panel handles input only over visible interactive character or bubble regions and never takes keyboard focus during ordinary interaction.
- Presence has three durable states: Roaming, Parked, and Hidden. A Voice Session temporarily overlays Connecting, Listening, Thinking, Speaking, Muted, Error, and Ending.
- Summon from Hidden reveals the Companion temporarily. End restores the exact prior durable presence state. Hide during voice ends the session before hiding.
- One Companion exists across every connected display topology. Autonomous Roaming stays within one display, while Summon and Move to Current Display may relocate through a short edge fade.
- Display bounds are terrain. Application windows, visible pixels, desktop content, input activity, and semantic context are never observed.
- The current display's safe visible bounds constrain movement and bubble placement. Display topology changes clamp the Companion to a reachable position.
- Existing manifests are authoritative. Assets are preloaded and validated before character presentation.
- Movement updates at display refresh rate, sprite frames use manifest frame rates, and positions align to device pixels.
- A 128-point sprite canvas is the initial visual scale. The final scale remains tunable through visual acceptance testing.
- Orion and Athena each use a capability-constrained motion graph. Unsupported transitions are prohibited or hidden behind display edges and short fades.
- OpenAI Realtime speech-to-speech uses WebRTC. Model and voice are configuration values, and semantic VAD initially uses low eagerness.
- The person always speaks first. Barge-in cancels model playback and stale buffered output.
- A failed session closes the microphone and requires explicit Retry. V1 never silently recovers a Voice Session.
- The standard OpenAI API key remains inside a Node.js 24 LTS TypeScript broker bound to loopback.
- The launcher removes the standard key from the app environment. The app authenticates to the broker with a random per-launch bearer and receives only a short-lived client secret.
- The broker exposes only health and client-secret operations, allowlists session configuration, logs no secrets or conversation data, and never proxies audio.
- `CompanionRuntime` is the highest application Module and the single high behavioral Seam.
- The `CompanionRuntime` Interface accepts launch, Summon, End, Roam, Park, Hide, Show, drag, character selection, display changes, platform lifecycle events, and Quit.
- Observable runtime snapshots expose presence, placement, animation, Voice Session state, bubble state, and recoverable errors without exposing Implementation details.
- The `CompanionRuntime` Implementation hides the Presence Director, Motion Director, Desktop Stage, Voice Session, and Preferences Modules.
- Stage rendering, Realtime voice, credentials, platform lifecycle, clock, and randomness sit behind narrow ports with production and deterministic test Adapters.
- Status Menu, shortcut, and character interaction Adapters translate person actions into the same runtime commands and own no product state.
- Local persistence is limited to safe interface preferences such as selected character, presence mode, shortcut, voice, volume, and reachable parked position.
- The development launcher supervises both app and broker. Status Menu Quit and terminal interruption perform the same complete cleanup.
- Delivery follows tracer-bullet vertical slices. The first slice proves packaging, rendering, click-through input, fake Summon, credential minting, WebRTC audio, and microphone teardown before the implementation deepens.

## Testing Decisions

- Tests verify externally observable behavior through public Interfaces rather than private Implementation details.
- TDD proceeds as repeated one-test, minimal-implementation cycles. Tests and implementation are not developed as separate horizontal phases.
- `CompanionRuntime` is the primary behavior Seam. Deterministic Adapters provide controlled voice events, credentials, display topology, lifecycle events, time, and randomness.
- App-shell tests exercise the packaged application with the real Status Menu, panel, accessibility hierarchy, shortcut registration, process lifecycle, and system integration.
- Manifest contract tests verify every required asset, dimension, anchor, frame rate, referenced state, and legal transition.
- Golden render tests cover all character states and transitions at 1x and 2x. Approved expected images are independent review artifacts rather than values derived during the test.
- A probe application behind the Companion verifies real click-through text selection, scrolling, dragging, resizing, and file-drop behavior.
- Deterministic scenarios cover Roaming, Park, drag-to-Park, Hide, Show, Summon, presence restoration, character switching, display changes, Spaces, full-screen, lock, sleep, wake, and Quit.
- Scripted Voice Session tests cover consent, Connecting, Listening, Thinking, Speaking, Mute, barge-in, timeouts, Retry, teardown, and every documented failure.
- Broker tests verify loopback binding, per-launch authentication, configuration allowlisting, standard-key isolation, secret redaction, direct media routing, and clean shutdown.
- Opt-in live OpenAI tests validate a ten-turn conversation, semantic turn-taking, barge-in, echo control, device changes, network interruption, latency, and teardown.
- Manual visual review covers the target Mac and an external display across light and dark appearance, busy backgrounds, Retina and mixed scale, negative display origins, Spaces, native full-screen, Stage Manager, Reduce Motion, and VoiceOver.
- Packaged-app end-to-end journeys include clean launch and Quit, duplicate launch, one-hour silent Roaming, first microphone consent, ten spoken turns, permission denial, network loss in every voice state, Hide and restoration, character switching, mixed-display topology, sleep, wake, and audio-device changes.
- Performance and privacy assertions are acceptance gates, not informational measurements.
- Any flaky automated test, formatting failure, lint failure, visual regression, leaked credential, stale microphone state, or unexplained resource regression blocks completion.
- The codebase is greenfield. The domain glossary, accepted ADRs, sprite manifests, this PRD, and independently approved golden renders are the prior art and sources of truth.

## Definition of Done

Current pass and pending evidence is tracked in the
[V1 acceptance ledger](../evaluation/v1-acceptance.md). A criterion remains
open until that ledger contains reproducible evidence for it.

Functional:

- One terminal command consistently produces one local app, one Status Menu,
  and one Companion.
- The Companion appears within 2 seconds after launch on the target Mac.
- Menu, shortcut, and character click can Summon from Roaming, Parked, and
  Hidden.
- Ending restores the previous presence state.
- No operation requests Screen Recording or any protected permission other
  than microphone.
- Provider and permission failures never break motion or require an app
  restart.
- Quit leaves no window, audio engine, broker, menu item, or process.

Motion and visual quality:

- Every allowed Orion and Athena path uses only supported states.
- No frame flash, crop jump, opaque rectangle, alpha halo, moonwalk, one-frame
  pose reversal, or visible unsupported transition remains.
- Grounded foot-anchor drift is at most 1 point.
- Transparent pixels and padding outside the hit region do not block
  underlying desktop actions.
- Bubble placement remains inside safe bounds and avoids the character's face,
  menu bar, and Dock.
- The waveform is refresh-smooth and agrees with real audio state.
- VoiceOver labels, keyboard operation, light and dark appearance, and Reduce
  Motion pass manual review.

Voice and privacy:

- The microphone is inactive before Summon and closes within 500 milliseconds
  after End, Hide, sleep, lock, Quit, or failure.
- A normal live exchange lasts at least ten turns and supports barge-in.
- Across 20 controlled turns on stable broadband, response audio starts within
  1.5 seconds median and 2.5 seconds at p95 after end of speech.
- Barge-in stops audible Companion speech within 250 milliseconds at p95.
- Natural pauses do not routinely commit turns prematurely.
- No start clipping, end clipping, echo loop, repeated segment, stale buffer,
  or overlapping old response is audible.
- Audio, transcript, conversation content, standard API key, and client secret
  never appear in local persistence or logs.
- Asking about the screen produces an honest screen-blind response.

Performance and resilience:

- Idle or Park CPU settles below 2 percent and ordinary Roaming below 5 percent
  on the baseline Apple Silicon Mac.
- Resident memory remains below 200 MB.
- A two-hour soak shows no continuous memory growth, duplicate runtime, lost
  character, blocked desktop input, or crash.
- Display changes, Space changes, full-screen, sleep, wake, lock, unlock, and
  audio-route changes leave the Companion reachable and the microphone closed
  unless a person explicitly starts a new session.
- All automated tests, formatting, and linting pass without flakiness.
